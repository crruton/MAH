# Петля самосовершенствования

Модель между сессиями ничего не помнит и не учится. Учится среда: барьеры, правила и скиллы. Поэтому вопрос «умнеет ли агент» превращается в измеримый: сходится ли среда.

## Путь одной ошибки

```
 агент делает действие
        │
        ▼
 1. ПОЙМАТЬ   guard.sh (хук), гейт CI, упавший вызов  ──►  событие в ~/.claude/harness/errors/*.jsonl
        │                                                  (барьер, исход, проект, сессия; секреты замаскированы)
        ▼
 2. ЗАМЕТИТЬ  ./harness.sh evolve: повтор 3+ раз за 7 дней,
              сигнатура упавшего вызова растёт и не закрыта барьером  ──►  кандидат
        ▼
 3. ЗАПИСАТЬ  evolve сам дописывает черновик в error.md (Found by: dashboard, Signature);
              агент получает задачу закрыть его скиллом error-to-rule
        ▼
 4. ЗАПРЕТИТЬ барьер против класса, на самом глубоком уровне (ОС > сервер > хук > текст)
              + атака-репро в try-it.sh: CI проверяет её на каждом push, барьер нельзя тихо сломать
        ▼
 5. НАУЧИТЬ   сообщение барьера говорит агенту, что делать вместо этого (в этой же сессии);
              строка правила в AGENTS.md или скилл (в следующих сессиях)
        ▼
 6. ПРОВЕРИТЬ дашборд: попытки этого барьера после инцидента
              0 за 7+ дней ─► «агент не пытается»
              > 0          ─► «барьер держит, агент пытается»: поправить инструкцию из шага 5
              новый инцидент через тот же барьер ─► «утечка»: барьер узкий, назад к шагу 4
```

## Почему ошибка не повторяется

Две разные гарантии, и их нельзя путать.

| Гарантия | Чем обеспечена | Насколько твёрдая |
|---|---|---|
| Ошибка **не попадёт в код** | барьер: хук не выполнит команду, гейт не пропустит MR, репро в CI не даст ослабить барьер | твёрдая, пока барьер на уровне хука, сервера или ОС. Барьер-текст не гарантирует ничего, поэтому считаем Enforcement Ratio |
| Агент **не будет пытаться** | сообщение барьера и строка правила | не гарантия, а измерение: попытки после инцидента на дашборде |

Пример из этого репозитория: INC-2026-11-05-01 (`re.M` + `\s` читает следующую строку). Первое исправление было правкой кода, а не барьером, и через час та же ошибка повторилась в другом файле (INC-02). На дашборде INC-01 помечен «утечка». После INC-02 появился гейт B21: ошибка больше не проходит, но дашборд показывает, что агент всё ещё иногда пытается (2 срабатывания). Значит, следующий шаг — строка правила или скилл, а не ещё один барьер.

## Как понять, что агент становится лучше, а не только не повторяет старое

| Вопрос | Метрика на дашборде | Хороший тренд |
|---|---|---|
| Реже ошибается вообще, включая незнакомые места | ошибки инструментов на 100 вызовов (из журналов сессий) | падает |
| Знает правила и не пытается | срабатывания барьеров на 100 вызовов | падает |
| Ловит **новые** ошибки, а не только старые | «новые варианты»: барьер остановил команду, которую ещё не видел | > 0 и не растёт число утечек |
| Ошибки, которых не было | срабатывания барьеров без инцидента: барьер поставлен заранее, по типовым ошибкам (B28–B37) | каждое срабатывание — непрожитый инцидент |
| Новые виды ошибок становятся редкими | новые классы инцидентов по неделям | падает к нулю |
| Ошибку находит машина, а не человек | доля инцидентов с `Found by: barrier / gate / ci` | растёт |
| Правила проверяет машина | Enforcement Ratio | растёт |
| Дешевле | токены (без чтения кэша) и рубли на сессию (медиана) и за неделю, по курсу ЦБ РФ | падает |
| Быстрее | активное время сессии (паузы 5+ минут не считаются) | падает при том же объёме |
| Меньше нагрузка на человека | вопросы барьеров и отказы человека на сессию | падает |
| Где появится следующая ошибка | «следующие барьеры»: повторяющиеся сигнатуры упавших вызовов без барьера | список короткий |

«Предсказывать» здесь значит две проверяемые вещи: барьер пишется против класса и ловит варианты, которых ещё не было (новые варианты), а растущая сигнатура ошибки становится барьером до того, как стала инцидентом (следующие барьеры). Ничего сверх этого дашборд не утверждает.

## Корреляция и доказательство

Всё, что выше, — наблюдение за реальной работой: оно показывает, что эффект держится, но не доказывает его (менялись задачи, модель, команда). Доказательство — контролируемый A/B на задачах со скрытыми проверками: `./harness.sh bench`, а улучшение харнеса без человека — `./harness.sh h2` (метод Harness²). Подробно — [BENCH.md](BENCH.md).

Без человека петля крутится так (`./harness.sh install --auto-evolve`): в конце сессии `evolve` заводит черновики и задачи, в начале следующей агент получает одну строку «ждут N задач харнеса» и говорит о них человеку. Человек решает два вопроса: принять ли правку барьера (ревью MR) и ошибка ли это вообще (статус «принято»).

## Дашборд

```bash
./harness.sh dashboard                 # ~/.claude/harness/dashboard.html, все проекты
./harness.sh dashboard --repo ../shop  # добавить error.md ещё одного репозитория
./harness.sh dashboard --json          # те же цифры для CI или своего графика
```

Один HTML без внешних файлов, светлая и тёмная тема. Источники только локальные: журналы сессий Claude Code (`~/.claude/projects`), хранилище событий харнеса, `error.md` проектов. Хуки при этом не тратят ни миллисекунды на успешные вызовы: знаменатель (сколько всего было вызовов, токенов, рублей) берётся из журналов. Журналы хранят стоимость в долларах; дашборд пересчитывает её в рубли по курсу ЦБ РФ на сегодня (один GET к cbr.ru, ничего не отправляется), `HARNESS_USD_RUB` задаёт курс вручную, `HARNESS_OFFLINE=1` отключает сеть.

```bash
./harness.sh evolve .            # один оборот петли: черновики инцидентов + задачи для агента
./harness.sh evolve . --dry-run  # показать, ничего не записывая
```

`evolve` не пишет барьеры сам: он находит, что пора чинить, и формулирует задачу. Барьер пишет агент по скиллу `error-to-rule`, человек ревьюит MR. Запускать раз в день или в конце рабочей сессии.

Ограничения:
- журналы сессий есть только у Claude Code; для OpenCode дашборд покажет события и инциденты, но не знаменатель;
- сравнение «4 недели против 4» честно только при похожем объёме работы; при малом числе сессий плитка пишет «мало данных»;
- «ошибка инструмента» — это любой вызов с `is_error`, включая ожидаемый ненулевой код выхода (например, упавший тест в TDD). Тренд важнее абсолютного числа.
