# Процесс: агенты держат границы дрейфа проекта

Шесть шагов. У каждого есть вход, действия, артефакт и критерий выхода. Шаги 1 и 6 делаются один раз, шаги 2–5 — петля, которая крутится всё время жизни проекта.

```
 1. Базовая линия ──► 2. Ошибка → правило ──► 3. Командные границы ──► 4. Пайплайн проверок ──► 5. Замеры ──► 6. Фиксация
                          ▲                                                                        │
                          └──────────────────────── петля каждую неделю ───────────────────────────┘
```

---

## Шаг 1. Базовая линия

**Вход:** репозиторий, стек, рантайм агента (Claude Code, OpenCode или другой).

**Действия:**
1. `bash install.sh <repo>` — шаблоны, хуки, гейты.
2. Заполнить `AGENTS.md` проекта: стек, точные команды сборки и тестов, карта кода, правила. Не больше 150 строк, это оглавление, а не книга.
3. Положить глобальный слой (`templates/AGENTS.global.md`) в `~/.claude/CLAUDE.md` и `~/.config/opencode/AGENTS.md`. Источник — один файл в git, правки через MR.
4. Включить зоны (`zones/`): Green — агент делает сам, Yellow — с апрувом человека, Red — технический запрет.
5. Защитить `main` на сервере: push запрещён всем, merge — мейнтейнерам. Работа идёт в `dev`.
6. Снять нулевой замер: `python metrics/convergence.py --repo <repo>`.

**Артефакт:** `AGENTS.md`, `CLAUDE.md`, `.claude/settings.json`, `opencode.json`, `docs/adr/index.md`, первый отчёт метрик.

**Готово, когда:** агент в новой сессии сам находит правила и команды, push в `main` отклоняется сервером, метрики считаются.

## Шаг 2. Ошибка → правило

**Вход:** агент ошибся: сломал сборку, прочитал секрет, обошёл запрет, выдумал API, починил тест вместо кода.

**Действия:**
1. В течение 24 часов, пока память свежая, записать инцидент в `error.md` по шаблону.
2. Спросить: можно ли запретить это технически?
   - **Да** — барьер как можно глубже: права ОС > серверная блокировка > хук > deny в CLI. Строковый фильтр команд обходится через `sh -c`, поэтому он не последний рубеж.
   - **Нет** — 1–2 строки в правилах (`AGENTS.md` или `rules/*.md`), привязка к ADR.
3. Написать репро-тест: падает до барьера, проходит после.
4. Прогнать правку через ревью харнеса (`review/harness-review.md`).

**Артефакт:** запись в `error.md`, барьер, репро-тест.

**Готово, когда:** гейт `check-error-log.py` зелёный — у закрытого инцидента есть барьер и репро-тест.

Цена правила = цена инцидента × свежесть памяти. Правило, записанное через неделю, пишется по догадкам.

## Шаг 3. Командные границы

То, что работало для одного человека, ломается на пятерых и десятках агентов.

**Вход:** второй человек или второй параллельный агент.

**Действия:**
1. **Общий AGENTS.md.** Правки только через MR и ревью. Факт живёт в одном слое. Две одинаковые поправки агенту за неделю — это правило в файл, а не третья поправка в чате.
2. **Права через MCP.** Опасный ресурс (БД, GPU, PII, ядро продукта) агент получает только через MCP-сервер, который знает, что запрещено. Пример: `mcp/test_env_broker.py`.
3. **Аренда ресурсов.** Задачи — `SELECT … FOR UPDATE SKIP LOCKED`, heartbeat с TTL, сборщик зависших; файлы — аренда с TTL; провайдер LLM — семафор с коротким таймаутом и быстрым отказом.
4. **ADR — память решений.** Перед планом агент сверяет свои пути с `Applies To` принятых ADR и ссылается на них. Противоречие принятому ADR — стоп до нового ADR. Номер ADR выдаёт гейт, а не память агента (`check-adr-numbers.sh`).
5. **Спека до кода.** Нетривиальная задача начинается со спецификации (OpenSpec: propose → apply → archive). Нет кода без утверждённой спеки.

**Артефакт:** `docs/adr/`, `mcp/`, шаблон MR с полями `Relevant ADRs` и «Меняет принятое решение?».

**Готово, когда:** номера ADR уникальны, у каждого MR заполнены поля ADR, агенты не конфликтуют за ресурсы.

## Шаг 4. Пайплайн проверок

**Вход:** любое изменение агента.

**Путь изменения:** аренда задачи и файлов → работа в Green Zone своей ветки → `pre-push` и тесты по диффу → гейты (`gates/run-all.sh`) → индекс дрейфа архитектуры → MR в `dev` и ревью человека.

**Петля харнеса:** ошибка на любом шаге → `error.md` → правка харнеса → ревью по `review/harness-review.md` → карантинный арбитраж (`review/arbitration.md`) → merge правила.

**Артефакт:** зелёный пайплайн; для правок харнеса — отчёт ревью.

**Готово, когда:** нарушение блокирует среда, а не договорённость.

---

## Шаг 5. Замеры

**Вход:** история git за неделю.

**Действия:** раз в неделю:
- `./harness.sh metrics <repo>` — сходимость по истории git, `docs/metrics.md`;
- `./harness.sh errors <repo>` — какие барьеры сработали, что агент повторяет, `docs/errors.md`;
- `./harness.sh errors <repo> --suggest` — повторяющиеся ошибки превратить в инциденты (шаг 2);
- `./harness.sh budget <repo>` — цена харнеса: барьер, который не срабатывает, но стоит токенов или миллисекунд, — кандидат на удаление.

| Метрика | Что показывает | Хороший тренд |
|---|---|---|
| Доля коммитов-исправлений | Сколько работы уходит на починку | Падает |
| Пунктов правил в AGENTS.md | Разбухает ли харнес | Плато при росте кода |
| ADR накопленным итогом | Фиксируются ли решения | Растёт ступенями |
| Файлов с тестами | Покрытие поведения | Растёт |
| Повторные инциденты | Держат ли барьеры | 0 |
| Enforcement Ratio | Доля правил, которые проверяет машина | Растёт |

**Готово, когда:** тренд виден за 4+ недели. Если правил становится больше, а доля исправлений не падает, харнес копит противоречия: пора на ревью правил.

На ArcSpace за 18 недель: доля исправлений упала с ~50% до < 5% при росте потока коммитов в 5 раз, число правил держалось на 11–13 пунктах.

---

## Шаг 6. Фиксация

**Действия:**
1. Записать окружения и права агента в каждом: локальная машина, оркестрация, CI, прод.
2. Ветки: работа только в `dev`, `main` — прод, через MR `dev` → `main` и ручной деплой.
3. Перенести общие находки в глобальный слой через MR.

**Готово, когда:** новый человек разворачивает процесс по этому файлу без вопросов к автору.
