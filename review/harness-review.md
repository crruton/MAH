# Ревью правки харнеса

Правка харнеса — новое правило, хук, deny, скилл, MCP-ограничение — меняет поведение всех агентов сразу. Поэтому её ревьюят как эксперимент, а не как текст. Методы ниже взяты из [harness2](https://github.com/google-research/harness2) (Google Research, рекурсивная оптимизация харнеса) и перенесены на ручное ревью. Сам harness2 как систему мы не используем — только его методы проверки.

## 1. Предложить → проверить → собрать (Propose → Probe → Compose)
Правку не принимают по описанию. Её прогоняют на той же задаче, где случился инцидент, и решают по **разнице в поведении** двух прогонов: с правкой и без неё. Несколько кандидатов правки проверяются по отдельности, итог собирается из тех, что дали эффект.

## 2. Всегда сравнивать с базой
Оценивается и базовый харнес, и харнес с правкой, на одном наборе задач. «Стало хорошо» без цифры базы — не результат.

## 3. Менять одно, фиксировать остальное
Для сравнения фиксируются: набор задач, модель, исполнитель (Claude Code, OpenCode), версия харнеса, сид. Меняется только сама правка. Иначе непонятно, что сработало.

## 4. Подбирать на одних задачах, проверять на других
Набор эталонных задач делится пополам: на одной половине правку подбирают, на второй — проверяют. Правило, которое помогает только на задачах, где его придумали, — подгонка.

## 5. Изолировать проверяемого от критериев
Агент не должен видеть, чем его оценивают: тесты-оценщики, рубрики, эталонные ответы. В harness2 агент сам скачал рубрику задачи, хотя его об этом не просили. Отсюда два правила:
- каталоги с тестами-оценщиками — под CODEOWNERS, агент их не правит;
- ограничение сети ставится на уровне среды (egress-фаервол, DNS), а не настройкой инструмента.

## 6. Сбой проверки — «не оценено», а не ноль
Если прогон упал по инфраструктуре (лимит провайдера, таймаут стенда), результат помечается «не оценено» и не смешивается с качеством правки.

## 7. Уроки только с доказательством
В харнес попадает урок, за которым стоит инцидент и прогон: запись в `error.md`, репро-тест, разница в поведении. Каждая задача опирается только на уроки, принятые раньше неё, — без заглядывания вперёд.

## 8. Отчёт с условиями
К результату ревью прикладываются условия: модель, исполнитель, набор задач, ограничения сети, версия харнеса. Без них результат нельзя повторить.

## Чек-лист ревьюера
- [ ] Есть запись в `error.md` и репро-тест, который падает без правки.
- [ ] Прогон без правки и с правкой на той же задаче, разница описана.
- [ ] Проверено на задачах, на которых правку не подбирали.
- [ ] Агент не видел тестов-оценщиков; сеть ограничена средой.
- [ ] Упавшие по инфраструктуре прогоны помечены «не оценено».
- [ ] Указаны условия: модель, исполнитель, задачи, версия харнеса.
- [ ] Пройден карантинный арбитраж (`arbitration.md`).
