# self-harness

Процесс, в котором ИИ-агенты работают над проектом и сами держат границы его дрейфа. Здесь всё, чтобы взять этот процесс, развернуть у себя одной командой и попробовать.

*A process kit for AI coding agents (Claude Code, OpenCode): layered context, Red/Yellow/Green zones, hooks, CI gates, ADR memory, an error log that turns incidents into rules, harness review methods and weekly convergence metrics. One-button launcher. Docs are in Russian. MIT.*

> Харнес — это то, что мы забрали у агента: не просьба в промпте, а исполняемый запрет в среде. Каждое забранное право — один пойманный инцидент.

## Одна кнопка

```bash
git clone https://github.com/crruton/self-harness.git
```

**Windows:** дважды щёлкните `harness.cmd` — откроется меню. Нужен [Git for Windows](https://git-scm.com/download/win) (из него берётся bash).

**Linux / macOS:**

```bash
cd self-harness
./harness.sh
```

**Сразу в свой проект, без меню:**

```bash
./harness.sh start ../my-project          # Linux / macOS / Git Bash
harness.cmd start C:\work\my-project      # Windows, cmd или PowerShell
```

**Только посмотреть, без своего проекта:**

```bash
./harness.sh demo
```

Демо создаёт временный репозиторий, ставит в него харнес и показывает пять барьеров:

| # | Барьер | Что ловит |
|---|---|---|
| 1 | `pre-push` | push в `main` |
| 2 | `guard-tests.sh` | агент запускает полный набор тестов на каждую правку |
| 3 | `check-adr-numbers.sh` | два ADR с одним номером |
| 4 | `check-error-log.py` | инцидент закрыт без барьера и репро-теста |
| 5 | `check-rules-size.sh` | AGENTS.md разросся больше 150 строк |

### Требования

| Что | Зачем | Обязательно |
|---|---|---|
| git, bash | всё | да |
| Python 3.10+ | гейты, метрики | да |
| jq | хук `guard-tests.sh` для Claude Code | для Claude Code |
| Docker | нагрузочный тест | нет |
| Claude Code или OpenCode | рантайм агента | нет, правила — обычный Markdown |

`./harness.sh doctor` проверит всё сразу.

## Что делает «Старт»

`./harness.sh start <repo>` — это шаг 1 процесса, базовая линия:

1. **Проверка окружения** — git, Python, jq, Docker, рантаймы агентов, глобальный слой правил.
2. **Установка** — копирует шаблоны, зоны, хуки и гейты. Существующие файлы не трогает, только сообщает, что оставил как есть.
3. **Подключение git-хуков** — `core.hooksPath = .githooks`, push в `main` блокируется сразу.
4. **Прогон гейтов** — показывает, что проверяется и что уже не так.
5. **Нулевой замер метрик** — `docs/metrics.md` с метриками по неделям из истории git.
6. **Следующие шаги** — что заполнить руками.

Что появится в вашем репозитории:

```
AGENTS.md                          правила проекта для агента (шаблон, заполнить)
CLAUDE.md                          указатель на AGENTS.md для Claude Code
error.md                           журнал ошибок агента
CHANGELOG.md
opencode.json                      зоны для OpenCode
.claude/settings.json              зоны и хук для Claude Code
.claude/hooks/guard-tests.sh       запрет полного прогона тестов агентом
.githooks/pre-push                 запрет push в main
.github/pull_request_template.md   поля ADR в MR/PR
docs/adr/index.md                  каталог ADR
docs/adr/ADR-0000-template.md      шаблон ADR
docs/harness/                      методы ревью правок харнеса и арбитраж
docs/metrics.md                    метрики сходимости
gates/                             проверки для CI
metrics/convergence.py             расчёт метрик
```

После старта посмотрите `git status`, проверьте файлы и сделайте коммит — харнес живёт в репозитории и меняется через MR, как код.

## Процесс за 6 шагов

Полное описание со входом, действиями, артефактом и критерием выхода — в [PROCESS.md](PROCESS.md).

| # | Шаг | Что делаем | Команда | Готово, когда |
|---|---|---|---|---|
| 1 | Базовая линия | Слои контекста, зоны, метрики до первой строки кода | `start` | Агент сам находит правила, push в main отклоняется, метрики считаются |
| 2 | Ошибка → правило | Каждая ошибка агента за 24 часа становится барьером и тестом | `incident` | У закрытого инцидента есть барьер и репро-тест |
| 3 | Командные границы | Общий AGENTS.md через MR, права через MCP, аренда ресурсов, ADR, спека до кода | `adr` | Номера ADR уникальны, агенты не конфликтуют за ресурсы |
| 4 | Пайплайн проверок | Хуки и гейты на каждом шаге, ревью правок харнеса | `check` | Нарушение блокирует среда, а не договорённость |
| 5 | Замеры | Метрики сходимости раз в неделю, нагрузка на стенде | `metrics`, `loadtest` | Правила на плато, доля исправлений падает |
| 6 | Фиксация | Окружения, права, ветки dev/main записаны | — | Новый человек разворачивает процесс сам |

Шаги 2–5 — петля, которая крутится каждую неделю всё время жизни проекта.

## Внедрение: день, неделя, месяц

**День 1 — базовая линия**
1. `./harness.sh start <repo>`, посмотреть изменения, закоммитить.
2. Заполнить `AGENTS.md`: точные команды сборки и тестов, карта кода. До 150 строк — это оглавление, подробности ссылками.
3. Положить глобальный слой: `templates/AGENTS.global.md` → `~/.claude/CLAUDE.md` и `~/.config/opencode/AGENTS.md`. Источник держать в одном git-репозитории, правки через MR.
4. Защитить `main` на сервере: push — никто, merge — мейнтейнеры. Работать в `dev`.
5. Подключить гейты в CI: пример в [`ci/`](ci/).

**Неделя 1 — петля ошибок**
- Каждая ошибка агента → `./harness.sh incident <repo> "..."` в тот же день.
- Барьер ставить как можно глубже: права ОС > защита на сервере > хук > deny в CLI > строка в правилах.
- Две одинаковые поправки агенту за неделю — это правило в `AGENTS.md`, а не третья поправка в чате.
- В конце недели: `./harness.sh metrics <repo>`.

**Месяц 1 — команда**
- Второй человек или параллельный агент — сразу ADR через `./harness.sh adr`, номера проверяет гейт.
- Опасные ресурсы (общая БД, GPU, персональные данные) — только через MCP-сервер, пример в [`mcp/`](mcp/).
- Любую правку харнеса пропускать через [ревью](#ревью-правок-харнеса) и арбитраж.
- Смотреть тренд метрик за 4+ недели.

## Зоны и права агента

| Зона | Что | Механизм |
|---|---|---|
| **Green** — без подтверждения | чтение кода, поиск, локальная сборка, тесты по диффу, коммит в свою ветку | разрешено |
| **Yellow** — с апрувом человека | `git push`, сборка Docker, сетевые запросы, правка `.claude/*` и `opencode.json` | `ask` |
| **Red** — технический запрет | `.env` и секреты, `git reset --hard`, `git clean`, `rm -rf`, force-push | `deny` + права ФС + защита веток |

- Claude Code: [`zones/claude-settings.json`](zones/claude-settings.json) → `.claude/settings.json`.
- OpenCode: [`zones/opencode.json`](zones/opencode.json) → `opencode.json`.

Строковый фильтр команд останавливает случайность, но не изолирует среду: `sh -c 'git reset --hard'` его обходит. Для Red Zone deny в CLI — только первый рубеж; дальше права файловой системы (read-only монтирование в контейнер агента) и защита веток на сервере.

Личные разрешения (`.claude/settings.local.json`) — в `.gitignore`, только для удобства. Не копите там allow-правила: на нашем проекте их набралось 491 при 0 запретов.

## Гейты и CI

```bash
bash gates/run-all.sh        # или ./harness.sh check <repo>
```

| Гейт | Проверяет | Откуда взялся |
|---|---|---|
| `check-adr-numbers.sh` | номера ADR уникальны, подсказывает следующий свободный | два параллельных агента выпустили два разных ADR-044 |
| `check-error-log.py` | закрытый инцидент имеет барьер, уровень и репро-тест | правила, записанные «на потом», не появлялись |
| `check-rules-size.sh` | AGENTS.md и CLAUDE.md не больше 150 строк | контекстные файлы разрастались до книги и переставали читаться |

Подключение: [`ci/github-actions.yml`](ci/github-actions.yml), [`ci/gitlab-ci.yml`](ci/gitlab-ci.yml).

Хуки:
- `.githooks/pre-push` — push в `main` отклоняется ещё на машине. Серверная защита ветки всё равно обязательна: хук обходится через `--no-verify`.
- `.claude/hooks/guard-tests.sh` — агент не может запустить полный набор тестов (`go test ./...`, `npm test`, `pytest` и другие). Полный прогон — только явно: `CLAUDE_FULL_TESTS=1 <команда>`.

## Журнал ошибок: ошибка → правило

```bash
./harness.sh incident <repo> "агент запушил в main"
```

Создаёт запись `INC-ГГГГ-ММ-ДД-NN` в `error.md`. Поля: симптом, корень, класс, **барьер**, **уровень** (текст | хук | сервер | ОС), **репро-тест**, ADR, статус.

Правила:
1. Запись — в течение 24 часов, пока память свежая. Цена правила = цена инцидента × свежесть памяти.
2. Закрыть без барьера и репро-теста нельзя — это проверяет гейт.
3. Повтор того же класса — барьер был слабым, поднимаем уровень.
4. Логи — ссылкой и выжимкой, без секретов и персональных данных.

## ADR — память решений

```bash
./harness.sh adr <repo> "PostgreSQL как очередь задач"
```

Создаёт `docs/adr/NNNN-<slug>.md` со следующим свободным номером и строку в `docs/adr/index.md`.

Поля для агента:
- **Applies To** — пути, к которым относится решение. Перед планом агент сверяет с ними свои файлы.
- **Reconsider When** — измеримые триггеры пересмотра.
- **Supersedes** — история только дописывается, старый ADR помечается `SUPERSEDED`.

Чистый дифф с зелёными тестами, который молча отменяет принятое решение, — это дефект. Шаблон MR требует поля «Relevant ADRs» и «Меняет принятое решение? Да / Нет / Не уверен»; «Не уверен» одобряет только человек.

## Ревью правок харнеса

Правка харнеса меняет поведение всех агентов сразу, поэтому её ревьюят как эксперимент. Методы взяты из [harness2](https://github.com/google-research/harness2) (Google Research) и перенесены на ручное ревью — сам фреймворк не нужен.

1. **Контраст прогонов** — та же задача с правкой и без, решаем по разнице в поведении.
2. **Всегда с базой** — оцениваем и базовый харнес, и с правкой.
3. **Меняем одно** — задачи, модель, исполнитель, версия харнеса зафиксированы.
4. **Отложенные задачи** — подбираем правку на одной половине задач, проверяем на другой.
5. **Агент не видит критерии** — тесты-оценщики под CODEOWNERS, сеть режет среда, а не настройка.
6. **Сбой ≠ ноль** — упал по инфраструктуре: «не оценено», а не провал правки.
7. **Уроки с доказательством** — в харнес только то, за чем стоят инцидент и прогон.
8. **Отчёт с условиями** — иначе результат не повторить.

После ревью — [карантинный арбитраж](review/arbitration.md): ловит ли барьер инцидент, не мешает ли нормальной работе, не ломает ли существующий код. Полный текст с чек-листом — [review/harness-review.md](review/harness-review.md).

## Метрики сходимости

```bash
./harness.sh metrics <repo>
```

| Метрика | Что показывает | Хороший тренд |
|---|---|---|
| `fix_share_pct` | доля коммитов-исправлений | падает |
| `rule_bullets` | пунктов правил в AGENTS.md | плато при росте кода |
| `adr_total` | ADR в репозитории | растёт ступенями |
| `test_files` | файлов с тестами | растёт |
| `commits`, `merges` | поток изменений | — |

Как читать: если правил становится больше, а доля исправлений не падает, харнес копит противоречия — пора на ревью правил. Исправления определяются по ключевым словам в сообщении коммита, это оценка, а не разметка.

## Нагрузочный тест

```bash
./harness.sh loadtest http://localhost:8080 100
```

Шаблон [`loadtest/k6-template.js`](loadtest/k6-template.js): смешанная нагрузка на путь чтения со ступенями 25% → 50% → 100% от цели. Замените `MIX` своими эндпоинтами. Гонять на изолированном стенде со своей БД, не на проде; наполнить БД до реалистичного объёма; эндпоинты с вызовами LLM мерить отдельно — их потолок задаёт провайдер.

## Частые проблемы

| Проблема | Решение |
|---|---|
| `harness.cmd`: «Git Bash not found» | установите Git for Windows |
| Хук Claude Code не срабатывает | нужен `jq` в PATH; проверьте `./harness.sh doctor` |
| push в main проходит | хук обходится `--no-verify`; включите защиту ветки на сервере |
| Установка «оставила существующие файлы» | так задумано: сравните свои файлы с `templates/` и перенесите нужное руками |
| Гейты красные после первого старта | это нормальная базовая линия: разберите нарушения или поднимите лимиты осознанно |
| Метрики пустые | в репозитории мало истории; смотрите тренд через несколько недель |
| `python` не найден в Windows | установите Python 3 и отметьте «Add to PATH» |

## Откуда это и что получилось

Процесс вырос из двух проектов:

- **Соло-этап** — SIP-платформа, один человек: каждая ошибка агента превращалась в правило; итог — 10 скиллов и 10 MCP-серверов. Шесть скиллов пережили переход в команду без изменений, четыре переделали — все в сторону машинной проверки вместо текста.
- **Командный этап** — ArcSpace, платформа системного архитектора: 5 инженеров, 37 ролей агентов, 18 недель истории.

Что показали замеры на ArcSpace:

| | Значение |
|---|---|
| Доля коммитов-исправлений | ~50% в июле–августе → < 5% в октябре |
| Поток коммитов | вырос в 5 раз |
| Пунктов правил в AGENTS.md | 11–13, шесть недель подряд |
| ADR | 60 |
| Автотестов | 618 |
| Нагрузка на путь чтения (2 vCPU) | 100 и 400 RPS без ошибок, p95 ≈ 6 мс |

Доклад: «Харнес, который написал сам себя», HighLoad++ 2026, Андрей Носов.
